# Subject screening: accuracy, task design and MoCA

October 2026. Branch `dev`, from commit `fc251f5`.

This note records which subjects the analyses keep, why, and what is known about the excluded ones.
Read it before changing a screen, re-running a fit, or writing the participant flow for the manuscript.
Tables are generated by `scripts/audit/a21_screening_tables.py`. That script checks itself against
`catalog.load_metadata`, so rerun it after any data or screen change instead of editing the tables by hand.

## Summary

- **Three screens decide who is analysed.** Two run at load time: accuracy (`min_easy_accuracy`) and task design
  (`prior_design_tolerance`). One is a fixed list applied at compile time: the manual MoCA list (`moca_rejection`).
- **Default load.** `catalog.load_trials()` and `load_metadata()` keep 34 PD patients (68 sessions) and 16 controls.
- **Removed for task design.** Eight subjects ran a session with the wrong priors: HC13, HC7, P9, P22, P28, P29, P32, P33.
  P3, P8 and P30 also fail it but are excluded for other reasons anyway.
- **Manual MoCA list.** It holds P2, P5, P8, P10, P14, P15, P16 and P21. The user computed it by hand, and no MoCA
  score for these patients exists anywhere in the data. They stay excluded. A strict MoCA ≤ 26 rule is **not** applied.
- **Stale results.** Results made before `cb58aff` (2026-10-17) still include the design-failing subjects: MCMC
  caches, DDM fits, GLM-HMM fits and `outputs/` tables. See [What is stale](#what-is-stale).

## Where each screen lives

| Screen | Rule | Code | Config | Stage | Switch off |
|---|---|---|---|---|---|
| Accuracy | Every biased-prior session ≥ threshold on valid 100%-coherence trials | `catalog.passing_subjects`, `src.utils.sessions.easy_accuracy_pct` | `BEHAVIOR.min_easy_accuracy` (0.6) | load time | `min_easy_accuracy=None` |
| Task design | Every session's prior colour splits 75:25 and its equal colour 50:50, each within the tolerance | `catalog.passing_subjects`, `src.utils.sessions.prior_design_error` | `BEHAVIOR.prior_design_tolerance` (0.05), `BEHAVIOR.prior_base_rates` ([.75, .5]) | load time | `prior_design_tolerance=None` |
| Manual MoCA list | Listed patients removed | notebook 0.10 (`reject_subject`) | `moca_rejection` | compile (0.10) | edit the config and re-run 0.10 onward |

Both load-time screens are applied per subject, not per session: one failing session removes the patient, so
OFF/ON pairs stay intact. Pipeline stages 0.20, 0.30 and 0.40 load with both screens off, so their files cover
every session. A new pipeline stage must do the same, or its file will lack rows for screened-out sessions.
The audit scripts in `scripts/audit/` also switch the design screen off, because the report handled those
sessions itself.

## Task-design check

### Why it exists

The task is meant to pair one colour whose targets go to the favoured side 75% of the time with one colour at
50:50. The pipeline infers the prior from the trial list (`get_prior_condition`). It picks the first colour that
is above 60% and calls the other colour "equal" without checking it. Sessions that ran something else were
therefore analysed as if they were normal. In particular, a session with a 75:25 prior on **both** colours
(to opposite sides) has its "equal" colour carrying a reversed prior, so prior use was measured against the
wrong baseline.

### How it is measured

`prior_design_error` uses every **presented** trial with a colour and a target, valid or not, because the design
is what was shown. Trial lists have fixed counts (typically 320 per colour, 240 to the favoured side), so correct
sessions match exactly or within a percentage point. The measure is the larger of the two departures, as a
proportion:

```
max( | |p_biased - 0.5| - 0.25 | ,  | |p_equal - 0.5| - 0 | )
```

Correct sessions score at most 0.017 (P1 OFF, which ran 682 trials). Off-design sessions score 0.0625 or more. The
tolerance of 0.05 sits in that gap.

### Harvard run-level investigation (2026-10-18)

Harvard sessions were run as one or more practice blocks plus about four trial blocks of 160 trials. Each block is a
separate file named `YYMMDD_HHMMSS.mat` under `raw/harvard_data/{pd,hc}/<subject>/{practice,trial}/`.
`scripts/audit/a22_harvard_runs.py` decodes every block (outputs `outputs/audit/a22_harvard_runs.csv` and
`a22_harvard_sessions.csv`).

**The correct pattern.** Practice blocks are 50:50 on both colours. Every trial block holds 80 trials of each colour,
with exactly 60 of 80 targets on the favoured side for the prior colour and 40 of 80 for the equal colour, and the
same condition in every block.

**The two-prior sessions were genuinely run that way.** They are not a combining or decoding error:

- **Every block, exact counts.** In each affected block, green sent exactly 60 of 80 targets right and red sent exactly
  20 of 80 right (condition "gr + rl"). This holds in every block of P30 ON, P28 OFF, P33 ON, P29 OFF, P32 ON and HC13,
  so the trial lists were generated that way.
- **Combining is correct.** 0.00 concatenates only the `trial/` blocks, sorted by file name (that is, by time), and
  compiled trial counts equal the sum of the blocks (e.g. P28 OFF: 160 + 160 + 55 + 160 + 160 = 695, the 55-trial block
  being an aborted run).
- **No event code records the setting.** Correct and two-prior blocks use identical codes in all ten event columns.

**When it happened.** All two-prior blocks fall between 2025-05-13 and 2025-06-10:

| Date | Session | Blocks |
|---|---|---|
| 2025-05-13 | P30 ON | gr + rl ×4 |
| 2025-05-16 | P32 OFF | gr ×4 (correct) |
| 2025-05-20 | P28 OFF | gr + rl ×5 (one aborted) |
| 2025-05-20 | P33 ON | gr + rl ×4 |
| 2025-05-21 | P29 OFF | gr + rl ×4 |
| 2025-05-30 | P31 ON | gr ×4 (correct) |
| 2025-06-03 | P30 OFF | gr ×4 (correct) |
| 2025-06-06 | P32 ON | gr + rl ×4 |
| 2025-06-06 | P28 ON | gl ×4 (correct) |
| 2025-06-10 07:22 | HC13 | gr + rl ×4 |
| 2025-06-10 10:34 | P33 OFF | block 1 gr + rl, blocks 2–4 gr |

- **Only red-prior sessions were affected.** In that window, every session with a red-left prior also had green set to
  75% right, while every green-prior session ran correctly. The red-prior sessions run in February and March (HC2 rl,
  HC7 rr, P25 OFF rl, P27 OFF rl, P25 ON rr) were correct, and no red-prior session was run in April.
- **The intended condition was probably red-left.** The extra prior is always green-right, and red-left fits each
  patient's counterbalancing (their other session used a different colour). This is an inference; confirm it from the
  task settings or run sheets.
- **It stopped on 2025-06-10 between 10:34 and 10:42.** P33 OFF's first block ran with both priors, and its next three
  blocks ran correctly as green-right. No two-prior block occurs after that.
- **A settings problem, not a code change between blocks.** The pattern fits per-colour prior settings that were not
  reset when a red prior was entered. The leftover-setting explanation fits P33 OFF (HC13, run that morning, had
  red-left set) but not P30 ON (the previous session, P29 ON, was green-left). A default of green-right fits both.

**Other block-level findings.**

- **HC7 (2025-02-28).** Block 1 ran with no prior (both colours 50:50) and block 2 is a one-trial aborted file. Blocks
  3–5 are correct red-right, which is why the combined session shows 68.75%.
- **Partial salvage.** HC7 could be analysed from blocks 3–5 only, and P33 OFF from blocks 2–4 only. Both participants
  then experienced 160 trials of a different condition first, and P33 still has no usable ON session, so neither is
  re-included by default.
- **Practice files not from their session (P25–P27; removed from raw 2026-10-19).** Notebook 0.02 compares each
  block's filename (program start), MAT header `Created on` (save) and `time` clock (monotonic, continuous through a
  session). 15 of the 21 practice files in P25 OFF/ON, P26 OFF/ON and P27 OFF/ON failed: their header dates fall 13–45
  days from the date in their names, which the task program cannot produce, so they were renamed, and all carry a
  filesystem date of 2025-04-29 against 2025-04-21 for the sessions' genuine files. Three were byte-identical copies
  (of HC7's and HC11's practice, and of P27 ON's own `250314_121934`). The other twelve were recorded on 2025-04-28:
  three at 10:09–10:24 on HC11's clock after HC11's session, nine at 10:57–11:33 after a ~13 min clock pause (the same
  laptop: that clock continues into HC12 and P31 OFF the next day). Their behaviour (78–100% valid, median RT 0.5–0.95 s)
  differs from these patients' genuine practice (23–70% valid, 1.1–1.3 s). They and HC16's duplicate folder
  `trial/h16_pract_2 last ones/` were removed from `raw/`; copies remain in `raw_backup_20261019/harvard_data/`.
  P25 ON, P26 ON and P27 OFF therefore have no recorded practice; whether they had a practice phase is to be asked of
  the Harvard team. Trial blocks were unaffected.

## MoCA

### The manual list

`config/main.yaml` carries `moca_rejection: [P2, P5, P8, P10, P14, P15, P16, P21]`, commented "low MoCA scores <= 26",
added in early 2025 (`aa8a32f`). Notebook 0.10 drops these patients before anything else runs.

- **Origin.** The user computed the list by hand.
- **No scores in the data.** None of the eight appears in any metadata file under raw, compiled or processed, nor in
  the older `compiled2/` and `processed2/` copies (90 files with a MoCA column were searched). Their scores cannot be
  recovered from the data, so the list stands.
- **Trial data exists for six of them.** P2, P8, P10, P14 and P16 have both sessions, and P15 has OFF only. P5 and
  P21 have no files. In the subject table, P14 (96% / 98%) and P16 (92% / 88%) would pass every other screen;
  only the list excludes them.

### Inconsistency with recorded scores

The list says "≤ 26", but it is not applied to the patients whose scores are recorded.

- **Analysed patients at or below 26.** At the default screens, P24 (20), P7 (24), P1, P11 and P19 (26 each) and
  LBR (23 ON, 29 OFF) all have a MoCA ≤ 26 and are analysed. P28 and P32 (26) are now out for task design.
- **Patients with no score.** The four kept Case Western patients and all controls have no MoCA recorded.
- **Scores that differ between sessions.** Some UCLA patients have one score per session, and they differ (LBR 23 / 29,
  COH 27 / 29, others by 1 point). The tables use the lower of the two.

A strict MoCA ≤ 26 rule is not applied anywhere. Its effect is shown in the site table below. If one is adopted,
implement it as another load-time screen in `passing_subjects` rather than extending the manual list. Either way,
the manuscript's participant flow must report the cognitive exclusion: the current Methods mention only the
accuracy screen.

## Other data-quality notes

- **P27 OFF is reversed.** It is correct on 51 of 154 trials at 100% coherence (33%), below chance at p = 3e-5,
  which looks like swapped response keys or reversed coding rather than poor performance. It is excluded by the
  accuracy screen. Check the session notes before any attempt to flip it.
- **Chance-level sessions.** P25 ON, P26 OFF, P26 ON, P27 ON and P30 ON are at chance at 100% coherence (49–56%),
  even though P30 scored 90% OFF.
- **P25 OFF has few valid trials.** Only 161 of 824 presented trials are valid.
- **Session order is incomplete.** It is unknown for the four Case Western patients, and COH has contradictory
  `off_med_first` flags on its two rows.
- **UCLA no-prior blocks.** The 8 UCLA patients with "eq" files (CG, COH, DP, FUR, LBR, MAR, MBY, SMI) ran a no-prior

  ends 0.9–3.9 min before the session on the clock), and the six `explicit/` OFF sessions as separate sessions
  (`<patient>_off_explicit`).
- **UCLA raw changes (2026-10-20).** `ucla_data/tremor-dominant/Trem_DCAM_OFFmeds_rr.mat` was restored from

- **Plot of the Harvard patients.** `outputs/audit/harvard_pd_psychometrics.png` (script

## What is stale

Everything computed before `cb58aff` used the 58-subject sample (40 PD, 18 HC). The design screen now removes
HC13, HC7, P9, P22, P28, P29, P32 and P33. Until rerun, the following still include them:

- **MCMC caches.** `processed/mcmc_fits` and the `outputs/` caches. `mcmc_cache.fit_or_load` refits automatically
  because the trial fingerprint changes.
- **DDM.** `processed/ddm/behavior_data.csv` (3.10) still holds the removed sessions. The per-session DDM fits of
  the remaining sessions stay valid, but group statistics change.
- **Shared GLM-HMM.** `processed/shared_glm_hmm` was fitted jointly across sessions, so it needs refitting.
- **Analysis outputs.** All `outputs/` tables and figures from the 2.x, 3.x and 4.x notebooks, including
  `participant_medication_effects.csv`.
